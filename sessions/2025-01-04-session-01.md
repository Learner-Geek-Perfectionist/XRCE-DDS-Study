## 📖 学习内容

### 文档: DDS-XRCE 规范 - Chapter 8

#### 8.1 General（协议概述）

**XRCE 协议设计目标**:
- 支持 40-100Kbps 低带宽网络
- 支持深度睡眠周期（设备可能每隔几分钟/天/月才活跃一次）
- 完整实现 < 100KB 代码
- 支持可靠和尽力传输

**与直接使用 DDS 的区别**:
- 没有标准 API（不可跨厂商移植）
- 必须依赖 Agent 才能工作
- 不直接点对点通信，全部由 Agent 代理

---

#### 8.2 Definitions（核心定义）

| 概念 | 定义 |
|------|------|
| **Message** | 传输层发送的信息单元，结构化字节序列 |
| **Session** | Client-Agent 之间通过握手建立的双向连接 |
| **Stream** | 会话内独立的、有序的消息流（可靠/尽力） |
| **Client** | 发起会话建立的实体（MCU 端） |
| **Agent** | 监听并接受会话请求的实体（SOC 端） |

**层次关系**: Client ↔ Agent → Session → Stream → Message

---

#### 8.3 Message Structure（消息结构）

**Message Header (4-8 字节)**:
```
┌──────────┬──────────┬─────────────┬───────────────────┐
│sessionId │ streamId │ sequenceNr  │ clientKey (可选)  │
│  (1B)    │  (1B)    │   (2B LE)   │    (4B)           │
└──────────┴──────────┴─────────────┴───────────────────┘
```

- sessionId ≤ 127 → 带 clientKey (8字节)
- sessionId > 127 → 不带 clientKey (4字节)

**Stream ID 规则**:
| 范围 | 类型 | 说明 |
|------|------|------|
| 0x00 | NONE | 不属于任何流 |
| 0x01 | BUILTIN_BEST_EFFORTS | 内建尽力流 |
| 0x02-0x7F | Best-Effort | 用户尽力流 |
| 0x80 | BUILTIN_RELIABLE | 内建可靠流 |
| 0x81-0xFF | Reliable | 用户可靠流 |

**Submessage Header (4 字节)**:
```
┌───────────────┬───────┬─────────────────┐
│ submessageId  │ flags │ submessageLength│
│    (1B)       │ (1B)  │    (2B LE)      │
└───────────────┴───────┴─────────────────┘
```

**16 种 Submessage 类型**:
- CREATE_CLIENT (0) / STATUS_AGENT (4) - 会话建立
- CREATE (1) / STATUS (5) - 对象创建
- WRITE_DATA (7) / DATA (9) - 数据传输
- ACKNACK (10) / HEARTBEAT (11) - 可靠传输机制
- FRAGMENT (13) - 分片传输

### 抓包验证 (hello_world.pcap)

#### Frame 1350-1351: 会话建立握手

**CREATE_CLIENT (Frame 1350)**:
```
Header: sessionId=0x80 (无会话), streamId=0x00 (NONE)
Payload: client_key=0xccccdddd, session_id=0x81
```

**STATUS_AGENT (Frame 1351)**:
```
Header: sessionId=0x81 (会话已建立!), streamId=0x00
Payload: result=STATUS_OK, xrce_cookie="XRCE"
```

#### Frame 1353: 批量创建对象

一条消息包含 4 个 CREATE 子消息：
```
Stream: 0x80 (BUILTIN_RELIABLE) ← 创建操作走可靠流

Submessage 1: CREATE Participant (object_id=0x0011)
  XML: <dds><participant><name>default_xrce_participant</name></participant></dds>

Submessage 2: CREATE Topic (object_id=0x0012)
  XML: <dds><topic><name>HelloWorldTopic</name><dataType>HelloWorld</dataType></topic></dds>

Submessage 3: CREATE Subscriber (object_id=0x0014)

Submessage 4: CREATE DataReader (object_id=0x0016)
  XML: <dds><data_reader><topic><name>HelloWorldTopic</name>...</topic></data_reader></dds>
```

---

### ObjectId 结构

```
ObjectId (16 位) = ObjectIdPrefix (12 位) + ObjectKind (4 位)

例: 0x0015 = prefix:0x001 + kind:0x5 (DATAWRITER)
```

**设计目的**: 
- 从 ID 直接看出对象类型
- 类似 DDS GUID 的精简版（128位 → 16位）
- ObjectId 是 Client 端概念，Agent 内部映射到完整 GUID

---

### 关键理解

**Header vs Payload 的区别**:
- Header 中的字段 = 消息**当前状态**（路由信息）
- Payload 中的字段 = **请求参数**（业务数据）

例: CREATE_CLIENT 时：
- Header.sessionId = 0x80 ("我还没有会话")
- Payload.session_id = 0x81 ("我想建立 0x81 会话")

**BUILTIN Stream 的意义**:
- 0x01 和 0x80 是会话建立时自动可用的流
- 其他 Stream ID 需要双方都分配资源
- 简单应用只用内建流即可

## 💡 心得体会

今天通过"协议规范 + 抓包验证"的学习方式，真正理解了 XRCE 协议的设计精髓：

1. **极致精简**: 每个字段都精心设计，如 streamId 的最高位就是可靠性标志
2. **分层解耦**: Header 负责路由，Payload 负责业务，清晰分离
3. **批量高效**: 一条 Message 可包含多个 Submessage，减少网络往返
4. **Client 极简**: ObjectId 只有 2 字节，复杂性全交给 Agent

最大的收获是理解了 **"Header 是现在的状态，Payload 是想要达成的目标"** 这个关键区别，之前一直困惑为什么 CREATE_CLIENT 的 Payload 里还要再放 session_id。
