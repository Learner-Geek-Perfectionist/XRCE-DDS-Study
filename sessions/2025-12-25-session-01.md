### 2. QoS 兼容性规则

**核心规则**：Publisher QoS ≥ Subscriber QoS

| Publisher | Subscriber | 结果 |
|-----------|------------|------|
| RELIABLE | RELIABLE | ✅ 通信 |
| RELIABLE | BEST_EFFORT | ✅ 通信 |
| BEST_EFFORT | BEST_EFFORT | ✅ 通信 |
| BEST_EFFORT | RELIABLE | ❌ 无法通信 |

同理适用于：
- **Durability**: TRANSIENT_LOCAL > VOLATILE
- **Ownership**: 两端必须一致

### 3. XRCE Client 三种实体创建模式

#### 模式对比

| 模式 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **XML** | Client 发送 XML 字符串 | 灵活 | 占带宽和内存 |
| **Reference** | Client 发送名称，Agent 有预配置 | 节省带宽，便于管理 | 需要预配置 Agent |
| **Binary** | Client 发送 `uxrQoS_t` 结构体 | 最节省带宽 | QoS 选项有限 |

#### Binary 模式示例

```c
uxrQoS_t qos = {
    .reliability = UXR_RELIABILITY_RELIABLE,
    .durability = UXR_DURABILITY_TRANSIENT_LOCAL,
    .history = UXR_HISTORY_KEEP_LAST,
    .depth = 10
};
uxr_buffer_create_datawriter_bin(&session, stream, dw_id, pub_id, topic_id, qos, UXR_REPLACE);
```

#### Reference 模式示例

Agent 的 `agent.refs`：
```xml
<data_writer profile_name="my_datawriter">
    <topic><name>Square</name><dataType>ShapeType</dataType></topic>
    <qos>
        <reliability><kind>RELIABLE</kind></reliability>
        <durability><kind>VOLATILE</kind></durability>
    </qos>
</data_writer>
```

Client 代码：
```c
uxr_buffer_create_datawriter_ref(&session, stream, dw_id, pub_id, "my_datawriter", UXR_REPLACE);
```

### 4. 抓包分析（hello_world.pcap）

#### XRCE 消息结构

```
┌─────────────────┬─────────────────┬─────────────────┬─────────────────┐
│   Session ID    │    Stream ID    │  Sequence Num   │   Submessage    │
│   (1-4 bytes)   │    (1 byte)     │   (2 bytes)     │   (variable)    │
└─────────────────┴─────────────────┴─────────────────┴─────────────────┘
```

#### Submessage 结构

```
┌─────────────────┬─────────────────┬─────────────────┬─────────────────┐
│  Submessage ID  │     Flags       │     Length      │     Payload     │
│   (1 byte)      │    (1 byte)     │   (2 bytes)     │   (variable)    │
└─────────────────┴─────────────────┴─────────────────┴─────────────────┘
```

#### 关键 Submessage ID

| ID | 名称 | 方向 |
|----|------|------|
| 0x00 | CREATE_CLIENT | Client → Agent |
| 0x01 | CREATE_PARTICIPANT | Client → Agent |
| 0x02 | CREATE_TOPIC | Client → Agent |
| 0x07 | WRITE_DATA | Client → Agent |
| 0x09 | DATA | Agent → Client |

#### hello_world.pcap 关键帧

| 帧号 | 内容 |
|------|------|
| 初期 | Session 建立、实体创建 |
| 2087 | Client 发送 `WRITE_DATA`，包含 "Hello DDS world!" |
| 2251+ | Agent 转发给其他 Client |

### 5. 核心概念澄清

#### Topic 实体 vs Topic 数据

| 概念 | 类比 | 位置 | 生命周期 |
|------|------|------|----------|
| **Topic 实体** | 📬 邮箱 | Agent（DDS 网络） | 持久存在 |
| **Topic 数据** | ✉️ 信件 | Client 产生 | 发送后消耗 |

#### Topic 类型 vs Topic 名称

```
Topic = 名称 + 类型

名称 (Name): "HelloWorldTopic"  ← 通信通道标识
类型 (Type): HelloWorld { index: uint32, message: string } ← 数据结构
```

- **类型定义**：通过 IDL 文件定义，使用 microxrceddsgen 生成 C 代码
- **名称**：运行时指定，用于匹配 Publisher 和 Subscriber

#### XRCE 类似 RPC

```
Client                           Agent                          DDS Network
  │                                │                                │
  │ ──── WRITE_DATA(data) ──────► │                                │
  │                                │ ────── publish(data) ────────► │
  │                                │                                │
  │ ◄─── DATA(sample) ──────────── │ ◄────── on_data_available ──── │
  │                                │                                │
```

## 📚 关键理解

### 1. 为什么 Topic 实体在 Agent，数据在 Client？

> XRCE-DDS 的设计目标是让**资源受限的 MCU**（Client）能够参与 DDS 通信。
> 
> - **Client** 只负责产生/消费数据，尽量轻量
> - **Agent** 运行在资源丰富的设备上，承担 DDS 实体管理的重任
> - Client 通过类似 RPC 的请求，让 Agent 代为创建实体和发布数据

### 2. QoS 兼容性的意义

> DDS 是分布式系统，Publisher 和 Subscriber 可能有不同的需求：
> 
> - **RELIABLE Subscriber** 期望收到所有数据 → Publisher 必须能保证
> - **BEST_EFFORT Subscriber** 可以接受丢包 → 对 Publisher 无要求
> 
> 因此规则是：Publisher 的承诺 ≥ Subscriber 的期望

### 3. 三种创建模式的选择

| 场景 | 推荐模式 |
|------|----------|
| 开发/调试阶段 | XML（灵活） |
| 生产环境 | Reference（集中管理） |
| 极度资源受限 | Binary（最小开销） |

## 📝 心得体会

1. **理解 Topic 的双重含义**：Topic 既是"实体"（通信通道的定义），又是"数据"（实际传输的消息）。混淆这两个概念会导致对 XRCE 架构的误解。

2. **XRCE 是 RPC 风格的协议**：Client 不直接参与 DDS，而是通过 Agent 代理。理解这一点对于调试和优化至关重要。

3. **QoS 是 DDS 的核心**：不同于传统消息队列，DDS 的 QoS 决定了通信的行为和可靠性。

4. **抓包是理解协议的最佳方式**：通过分析实际的网络流量，可以直观地看到协议的工作方式。
